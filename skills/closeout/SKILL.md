# /closeout — Session 收场（全局版）

一次 session 的成果只活在聊天记录里等于没发生 —— 下一个 session（或并行的另一个 agent）看不到。
收场的目的：把「做了什么 / 为什么 / 验证结果 / 未决事项」写进仓库，让任何人能接续。

## 第 0 步：判断要不要收

- **只读任务**（问答 / 审计 / 调查 / 解释代码，仓库无修改）：不收。制造空 commit 和空日志是噪音。告诉用户本次无仓库改动、无需收场即可。
- 有仓库修改：先 `git rev-parse --show-toplevel` 确认项目根（后续路径都基于它，别信 CWD 一定指向主仓库），再 `git status --short` + `git log --oneline -5` 看清本次改了什么、哪些已提交。
- **用户明确要求收尾** → 直接执行。**已授权的仓库改动** → 完成项目要求的记录、验证和本地提交，不为同一范围的收尾重复索取授权。新建协议、扩大修改范围或对外发布仍按用户授权处理。无 Git 的文件任务只验证成果并交接，不初始化仓库。

## 第 1 步：探测协议（在项目根按序检查，命中即用，不再往下）

| 序 | 条件 | 模式 |
|---|---|---|
| 0 | `.claude/commands/closeout.md` 存在 | **项目自有版** —— 读它、完整按它执行。项目版是该仓库的真源，全局版让位 |
| 1 | `logs/unreleased/` 目录存在 | **changeset 模式** |
| 2 | `docs/SESSION_LOG.md` 存在，且文件头部（前 10 行）无「冻结」字样 | **session-log 模式** |
| 3 | 都没有 | **lite 模式** |

为什么 SESSION_LOG 要查冻结标记：有的项目已把 SESSION_LOG 归档停写、改用 changeset（全局连续编号在多 agent 并行时会撞号）。往冻结文件里追加是违规操作，不是补救。

## changeset 模式

1. **模板真源是项目里的 `logs/unreleased/README.md`** —— 先读它。文件名格式、必填字段、hash 规则以它为准，各项目会有差异，不要凭记忆或本 skill 的示例写。
2. 在 `logs/unreleased/` 新建**独立文件**记录本次工作（改了什么 / 为什么 / 验证证据 / 关联 PR·ADR）。绝不追加别人的文件，绝不手写任何全局连续编号（`Session #N` / `LOG-NNN` / `CL-NNN`）—— 连续编号只由发布脚本单点生成，手写就会在并行 session 之间撞号，这正是 changeset 模式要根除的病。
3. `docs/PROGRESS.md` 存在则更新顶部待办：完成项打 ✅ 或删除，新发现按优先级插入。记**状态**，不记流水。
4. 校验：`package.json` 里有 `changelog:validate` 脚本就跑它，红了按报错修，不许跳过。
5. **收口提醒**：数一下 `logs/unreleased/` 里的 changeset 数（去掉 README / TEMPLATE），超过 50 条就在收尾汇报里提醒用户：已积压 N 条，该跑 `changelog:release` 收口了。这一步别省 —— 收口没有别的触发时机，全靠收场时提醒。

## session-log 模式

1. 先确认日志未冻结，并读取项目的现行日志格式。沿用项目提供的编号生成器；不得手写或推算全局连续编号。项目没有安全编号机制时，用其允许的日期/工作键格式；若格式不兼容，说明冲突并保留 Git 提交作为本次记录，不擅自迁移整套协议。
2. 仅在项目允许且有应记录的改动时追加条目，覆盖：本次完成 / 未决·阻塞 / 下次起点 / 关键决策 / 文件变更 summary。只读、无产出的任务不制造日志或空提交。
3. `docs/PROGRESS.md` 存在则按 changeset 模式第 3 步同样更新。
4. **迁移提示**：若发现编号有跳号或字母后缀（撞号补救的痕迹），或 `git worktree list` 显示多个并行工作树，在收尾汇报里提示用户：此项目适合迁移到 changeset 模式（全局唯一文件名根除编号竞争），可参考已迁移项目的 `logs/unreleased/` 机制。

## lite 模式

项目没有收场协议，不代表不用收 —— 代表 **git 本身就是它的日志**。

1. 把本次工作以 conventional commit 落库（`feat(scope):` / `fix:` / `docs:` …），**commit body 就是 session 记录**：做了什么、为什么、怎么验证的、有什么未决。多段工作按逻辑拆原子 commit。
2. 项目已有自己的日志惯例（如 `docs/worklogs/`、`NOTES.md`）→ 按既有惯例追加一条，格式跟随已有条目。
3. **不要擅自创建** `docs/SESSION_LOG.md` / `docs/PROGRESS.md` / `logs/unreleased/`。上协议是项目决策，不是收场的副作用；用户明确要求时才脚手架。

## 通用纪律（三种模式共用）

- **Git/GitHub 边界**：遵守机器规则中的归属边界；已有项目各自提交，不向上层重复收录。混合目录禁止全部暂存/提交，必须逐项核对本任务内容；本地收尾不授权首次上传、新建远端或扩大上传范围，既有授权范围继续有效。

- **ADR 门槛**：本次产生了架构决策（2+ 子系统接口变更 / 新外部依赖·服务 / 数据模型结构变化），且项目有 `docs/DECISIONS.md` → 追加 ADR（项目有 `/decide` 命令就按它起草）。bug fix / 单文件重构不算，别为凑仪式感写 ADR。
- **按归属暂存**：先检查开工基线与完整 diff。逐个点名文件；若同一文件含其他任务改动，使用隔离 worktree 或只暂存本任务 hunks。`git diff --quiet` 只能证明文件变了，不能证明改动归属；禁止据此暂存整个共享文件。提交前检查 `git diff --cached`。
- **禁 `--amend` 并入上一个收场 commit**，禁把多个 session 合并成一个 commit —— 收场 commit 是审计线，粒度丢了不可逆。
- 收尾 commit 信息用 conventional 格式（如 `docs: closeout changeset`）。

## 收尾汇报

汇报有两个读者，分开写，别混成一段协议术语：

**① 账目（给审计看）** —— 逐条一行，不展开解释：写了哪个文件（changeset 文件名 / Session #N / commit hash）、PROGRESS 动了什么、有没有 ADR、校验结果、（changeset 模式）当前积压数。作用是让人扫一眼确认没漏步，所以越紧凑越好。

**② 一句人话（给正要合上电脑的人看）** —— 最后单独一句，交代 **做了什么 · 有多大 · 下次从哪接**。

写这句时设想读的人不知道 changeset 是什么、不关心 hash，明天早上只想知道「昨天到哪了、今天从哪开始」。所以句子里不出现 changeset id、commit hash、模式名、脚本名、ADR 编号，用日常动词。有没做完、没验证、绕过去的，也在这句里说出来 —— 这是当天的实话总结，不是喜报。

> 修了收场 skill 的协议探测，动了 3 个文件，下次接着补单元测试。
> 把登录超时的坑填了，改了 2 个文件加 1 条决策记录，下次回头确认限流那块还漏没漏。
> 今天只整理了文档没动代码，PDA 异常落地页还卡在接口没定，下次从那儿继续。

账目回答「存好了吗」，人话回答「我到哪了」。只给账目，人得自己翻译一遍；只给人话，出问题时查不到证据。两个都要。

## 文件交接

有实际产物时，按机器规则和项目已有 handoff 说明权威路径、来源版本、验证结果、未决事项与下一位操作者的步骤；交代本任务临时文件的保留或清理情况。不向冻结包里补写说明，不为普通问答另建交接文档。
